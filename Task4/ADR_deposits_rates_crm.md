После обновления ставок в кэше запускается встроенный процесс экспорта. <br> 2. Кэш формирует файл ставок (CSV/JSON) и добавляет версию/время формирования. <br> 3. Партнёрская система загружает файл в свой справочник для консультаций. |
| UC-DR4 | Клиент, Сотрудник кол-центра           | Консультация клиента по депозиту       | 1. Клиент обращается по телефону. <br> 2. Сотрудник использует CRM для получения ставок. <br> 3. Клиент получает консультацию на основании актуальных условий.                |


### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**
| **№** | **Требование**                                                                    |
| :---: | :-------------------------------------------------------------------------------- |
|   R1  | Доступность кэша ставок не ниже 99,9%                          |
|   R2  | Запрещено прямое чтение ставок из АБС клиентскими каналами и CRM                  |
|   R3  | Недоступность АБС не должна блокировать консультации (работа из кэша)             |
|   R4  | Должны быть реализованы метрики: время последнего обновления, успешность экспорта |
|   R5  | Экспортный файл не должен содержать персональных данных                           |
|   R6  | Доступ к ставкам в CRM должен быть ограничен ролевой моделью                      |
|   P1  | Формирование файла не должно влиять на производительность кэша                    |
|   S1  | Формат файла должен быть документирован и версионирован                           |
|   S2  | Логи формирования и передачи файла должны быть централизованы                     |
| +R1 | Партнёрский кол-центр не поддерживает API-интеграцию — допускается только файловый обмен. |
| +R2 | Передача файла должна осуществляться через защищённую зону обмена банка (без прямого доступа партнёра во внутренний контур). |
| +R3 | Решение должно быть реализовано в рамках MVP без внедрения новой интеграционной платформы (ESB, Kafka и т.п.). |
| +R8 | Все каналы должны использовать единый кэш как read-модель |

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. Прямой доступ CRM к АБС

Отказ: Cоздаёт риск деградации Oracle (P5), нарушает +R8.

2. Формирование файлов напрямую из АБС

Отказ: увеличивает нагрузку на АБС, нарушает принцип защиты ядра.

3. Создание отдельной БД ставок для кол-центра

Отказ: появление второго источника истины и риск рассинхронизации.

4. API-интеграция партнёра

Отказ: технически невозможна (ограничение — только файлы), нарушает +R1.

**Недостатки, ограничения, риски**

1. Риск неактуальности данных

Файл для партнёра может отставать от состояния кэша на время регламентной выгрузки.

2. Операционные риски

Появляется дополнительная зона мониторинга — экспорт файлов.

3. Риск рассинхронизации

При сбое синхронизации АБС → Кэш партнёр и CRM будут видеть устаревшие ставки.

4. Файловая интеграция

Отсутствие онлайн-проверки статуса получения файла партнёром.

5. Усложнение поддержки

Необходим контроль версий формата файла и регламентов передачи.
