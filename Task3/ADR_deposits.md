## Обоснование решений

1. Разделить сценарии чтения и записи: чтение ставок/продуктов только из кэша

Решение: каналы (Сайт, Интернет-банк) получают список депозитов и ставок только из кэша, синхронизируемого с АБС по расписанию/событиям.
Обоснование: выполнение P1/P2 и запрета +R8: миллисекундный отклик и отсутствие “справочник >1с”; защита АБС от пиков чтения, снижение нагрузки на Oracle (вертикальное масштабирование) и изоляция рисков деградации АБС.
Трассировка: P1, P2, P5, +R8, +R5, R1, R3, S3.

2. Интеграция интернет-банкинга и АБС через контрактный API 

Решение: заменить прямую интеграцию интернет-банка с БД АБС на интеграцию через контрактный API АБС.
Обоснование: снижение связанности и рисков изменений схемы, повышение безопасности (минимальный доступ + TLS), обеспечение наблюдаемости, идемпотентности и устойчивости, а также защита АБС (Oracle) от пиковых нагрузок за счёт отделения сценариев чтения (кэш) от сценариев записи (API).
Трассировка: P5, R4, R5, S2, S1, S3

3. Все внешние зависимости, влияющие на UX/устойчивость, сделать асинхронными: OTP/СМС, БКИ, кредитный конвейер

Решение: взаимодействия с OTP/2FA и SMS-шлюзом — асинхронные (как на схемах), без блокировки критического пути “клик → ответ”.
Обоснование: внешние провайдеры нестабильны по задержкам; асинхронность и ретраи защищают каналы и АБС от зависаний и каскадных отказов, соответствуют +R7 и P1/P5.
Трассировка: +R7, P1, P5, R1, R3, R4.



### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. Прямая синхронная интеграция каналов с АБС (REST/SQL/PLSQL)

Суть: Интернет-банк и сайт на каждое действие обращаются напрямую к АБС за ставками/продуктами и регистрацией заявок.

Почему отказались:
Нарушает запрет на синхронные чтения из АБС (+R8), не защищает АБС от пиков нагрузки (P5, +R5), создаёт высокую связанность (R2) и риск деградации клиентских каналов при проблемах в АБС (R1, R3).

2. Чтение ставок напрямую из АБС через Integration API (без кэша)

Суть: Каналы получают продукты и ставки через контрактный API АБС, но без отдельного кэша.

Почему отказались:
Не решает проблему миллисекундного отклика (P1, P2), не устраняет зависимость производительности каналов от АБС и противоречит требованию исключить частые синхронные обращения к АБС (+R8, P5).

3. Полная событийная архитектура с Kafka и подпиской интернет-банка

Суть: Интернет-банк напрямую подключается к Kafka и строит read-модель ставок/статусов на основе событий АБС.

Почему отказались:
Текущая платформа интернет-банка несовместима с Kafka (+R3), что ведёт к существенным технологическим доработкам и риску выхода за рамки задачи.

4. Использование ESB/шины как центрального оркестратора процесса

Суть: Все каналы интегрируются с АБС через ESB, который оркестрирует вызовы, трансформации и маршрутизацию.

Почему отказались:
Не устраняет фундаментальную проблему нагрузки на АБС (если нет кэша), добавляет дополнительную точку отказа и усложняет архитектуру без решения ключевого требования по производительности (P1, P2, P5).

5. Синхронная регистрация заявки в АБС без Outbox (с повторными попытками в коде)

Суть: Интернет-банк сразу отправляет заявку в АБС, при ошибке выполняет ретраи в рамках процесса или фонового job.

Почему отказались:
Не гарантирует надёжную доставку при сбоях и рестартах (R4), усложняет обеспечение идемпотентности и устойчивости при отказах ЦОД (R3).

6. Полноценный workflow-движок (Saga/Orchestrator)

Суть: Процесс открытия депозита управляется внешним BPM/Workflow-движком.

Почему отказались:
Избыточно для текущего объёма сценария, существенно усложняет ландшафт и выходит за рамки задачи “только депозиты”, при том что требования R4/R8 решаются более простыми механизмами (Outbox + контрактный API).

**Недостатки, ограничения, риски**

Риски согласованности данных и “неактуальности” 

- Ставки/продукты в кэше могут отставать от “истины” в АБС (расписание/события/инциденты синхронизации). Это может привести к показу клиенту ставки, которая уже изменилась.
- Персональная ставка зависит от риска и может обновляться по расписанию: клиент увидит “вчерашнюю” персональную ставку до следующей синхронизации.
- Требуется явная политика: TTL/версии/время последнего обновления, а также поведение при рассинхроне (например, “показываем ставку + дисклеймер” или “блокируем открытие, если данные устарели”).

Сложность статусов и временная несогласованность процесса заявки

- При outbox/async доставка в АБС не мгновенная, поэтому пользователь увидит промежуточные состояния: Created → OTP Pending → Confirmed → Sending → RegisteredInABS. Это повышает сложность UX и поддержки.
- Возможны “скачки” статусов при повторной доставке/обработке событий или задержках.
- Если статусы “в канале” и “в АБС” не идеально выровнены, появляется риск нарушения R8 (единые статусы) на практике.

Риски дублирования операций (идемпотентность)
- Outbox по природе даёт повторные доставки (at-least-once). Без строгой идемпотентности на стороне Integration API АБС возможны: дубли заявок, повторные уведомления/СМС, двойные переходы статусов.
- Идемпотентность должна быть реализована не только для “создать заявку”, но и для всех команд “подтвердить/обновить/повторить”, иначе повторы будут “рвать” процесс.

Усложнение интеграций из-за “двух миров”: HTTP для IB и Kafka для АБС
В АБС добавили Kafka, а в IB — ограничение по Kafka. В итоге появляется гибрид:
- IB: outbox + HTTP в Integration API,
- АБС: Kafka для внутренних событий.
Это усложняет сквозную диагностику и требует явных мостов/адаптеров/процессов синхронизации.

Нагрузка на Integration API АБС и риск превращения его в “новую точку боли”

Перенос интеграций в контрактный API снижает связанность, но создаёт риск:
- API станет единственной точкой входа для каналов (узкое место),
- рост требований к SLA и масштабированию этого API,
- необходимость строгих лимитов/квот, иначе при пике каналов нагрузка всё равно “протолкнётся” к АБС (+R5).
Если API в итоге внутри обращается к тем же PL/SQL/Oracle синхронно без буферизации — эффект защиты АБС будет ограничен.
